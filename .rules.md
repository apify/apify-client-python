# Coding guidelines

This file provides guidance to programming agents when working with code in this repository.

Python client for the [Apify API](https://docs.apify.com/api/v2), published on PyPI as `apify-client`. `ApifyClient` (sync) and `ApifyClientAsync` (async) are the entry points.

## Development

- Tasks live under `[tool.poe.tasks]` in `pyproject.toml` and are described in `CONTRIBUTING.md`. Run them with `uv run poe <task>`; set up with `uv run poe install-dev`.
- `uv run poe check-code` runs lint, type-check, the async docstring check, and unit tests. Run a single test with `uv run pytest tests/unit/<path>.py::<test_name>`.
- Ruff, ty, and pytest settings are in `pyproject.toml`; docs examples (`docs/**/*.py`) have their own `docs/pyproject.toml`. Each docs example comes as a `_sync.py` / `_async.py` pair.
- Docstrings follow the Google style, and every module starts with `from __future__ import annotations`.
- `tests/unit` and `tests/integration` each have a `README.md` describing their rules and required tokens. Unit tests mock HTTP with `pytest-httpserver`:

```python
def test_example(httpserver: HTTPServer) -> None:
    httpserver.expect_request('/v2/endpoint').respond_with_json({'data': ...})
    client = ApifyClient(token='test', api_url=httpserver.url_for('/').removesuffix('/'))
    # assert client behavior
```

## Commits

[Conventional Commits](https://www.conventionalcommits.org/); the types are listed in `CONTRIBUTING.md`. Choose the type by *what* changed, not just *why*:

- `feat:` / `fix:` / `perf:` / `refactor:` / `style:` — **source code only**; these trigger a release and appear in the changelog
- `test:` — test additions or changes (no release)
- `docs:` — documentation changes; also triggers a docs release on master
- `ci:` — CI/workflow changes
- `chore:` — dependency bumps, tooling, generated files, and other housekeeping
- `build:` — build system changes

Logging changes are breaking: changing a log level, a logger name, or the wording of a log message, or removing one, breaks downstream log-based tooling. Keep the accurate commit type, add `!`, and list the changes in a `BREAKING CHANGE:` footer. With squash-merge the `!` must be in the PR title.

## Docs, comments, and tests

- Never edit `website/versioned_docs/`. Those snapshots are release-automation output, frozen against the code that shipped. Fix `docs/` and the next release snapshot carries the change.
- Write `RQ` for the request queue in comments and docstrings. Log messages and public `.mdx` docs spell out the full term.
- Comments and docstrings describe what the code does now. The bug a change fixed, what a PR changed, and contrasts with removed behavior (`instead of ...`, `no longer ...`) belong in the commit message.
- Don't explain language features in comments. A comment earns its place with a domain reason, an invariant the types can't express, or a non-obvious consequence for callers.
- Use single backticks for code references in docstrings and comments, never RST-style double backticks.
- Wrap docstrings and prose comments to the full line length configured in `pyproject.toml`.
- Write only ASCII in source files: `->` instead of an arrow, `-` instead of a dash, straight quotes.
- Write flat `def test_*()` functions, never `class Test*`, and no section-header comments between tests.
- Almost every test gets a one-line docstring stating what it verifies, without a `Regression test:`-style prefix.
- In `@pytest.mark.parametrize`, wrap each case in `pytest.param(..., id='...')` with an id that describes the case.
- Use `Mock` and the `monkeypatch` fixture for test doubles, not hand-rolled stubs, counters, or flags.
- A test that changes process-wide or event-loop-wide state restores it. Prefer `monkeypatch`; for APIs it can't patch (`loop.set_exception_handler()`, `signal.signal()`, logging config, `os.chdir()`), capture the original value and restore it in a `finally`.
- For a TCP endpoint that must refuse connections, bind a socket to `('127.0.0.1', 0)` and hold it open without calling `listen()`. A hard-coded port can be taken by a server in a parallel xdist worker. Test servers use `127.0.0.1`, since on Windows `localhost` resolves to both IPv4 and IPv6.

## Architecture

### Client hierarchy

Entry points return resource sub-clients, which can create child clients (e.g. `ActorClient.builds()` -> `BuildCollectionClient`):

```text
ApifyClient
├── .actor(id)    → ActorClient            (single resource operations)
├── .actors()     → ActorCollectionClient  (list/create)
├── .run(id)      → RunClient
└── ... (datasets, schedules, tasks, webhooks, key-value stores, request queues, etc.)
```

`ClientRegistry` / `ClientRegistryAsync` (`_client_registry.py`) hold the resource client classes and are passed to every client, so clients can create child clients without importing them (avoids circular imports). All resource clients derive from `ResourceClientBase` (`_resource_clients/_resource_client.py`), whose `WithLogDetailsClient` metaclass wraps public methods for structured logging.

### Sync/async symmetry

Every resource client in `src/apify_client/_resource_clients/` has its sync and async variant in the **same file** (e.g. `ActorClient` and `ActorClientAsync` in `actor.py`) with the same interface. Docstrings are written on the sync client only and copied to the async one: edit the sync docstring and run `uv run poe fix-docstrings`.

### HTTP layer

`HttpClient` / `HttpClientAsync` (`http_clients/_base.py`) hold the shared request pipeline (retries, timeouts, API errors); transports (`Impit*` default, `Httpx2*` behind the `httpx2` extra, or a custom one via `ApifyClient.with_custom_http_client()`) implement sending, error classification, and lifecycle hooks. Request-body compression lives in `http_compressors/`, selected by the `compression` constructor argument.

### Generated models

`_models.py`, `_typeddicts.py`, and `_literals.py` are **generated** from the OpenAPI spec by `datamodel-code-generator` (config in `pyproject.toml`, aliases in `datamodel_codegen_aliases.json`) and post-processed by `scripts/postprocess_generated_models.py`. Never edit them by hand; durable fixes go into the post-processing script.

- Each input-side TypedDict ships in a snake_case and a camelCase variant (`RequestResourceDict`, `RequestResourceCamelDict`); the camel variants are synthesized in the post-processing script, and resource-client signatures accept either casing or the Pydantic model.
- Regenerate with `uv run poe generate-models` (published spec) or `uv run poe generate-models-from-file <path>`. `scripts/openapi_spec.py` documents how the spec version is recorded. Don't commit a regeneration that only moves the recorded version, and don't commit models generated from a local spec file.
- The nightly `Regenerate models` workflow opens a `chore:` PR when the models change. Retitle it to `fix:` / `feat:` when the diff is user-facing, so it lands in the changelog and triggers a release.
