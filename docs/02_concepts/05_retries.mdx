The Apify client automatically retries requests that fail due to:

- Network errors
- Internal errors in the Apify API (HTTP status codes 500 and above)
- Rate limit errors (HTTP status code 429)

By default, the client retries a failed request up to 4 times. The retry intervals use an exponential backoff strategy:

- The first retry occurs after approximately 500 milliseconds.
- The second retry occurs after approximately 1,000 milliseconds, and so on.

You can customize this behavior using the following options in the <ApiLink to="class/ApifyClient">`ApifyClient`</ApiLink> constructor:

- `max_retries`: Defines the maximum number of retry attempts. Set it to `0` to disable retries.
- `min_delay_between_retries`: Sets the minimum delay between retries as a `timedelta`.

Retries with exponential backoff help reduce the load on the server and increase the chances of a successful request.

## Retry unprocessed requests in batch adds

When the API rate-limits a batch of added requests, it responds with HTTP 200 and lists the requests it skipped in `unprocessedRequests`. The client's HTTP retries don't apply to such a response, because it's a success. For this case, <ApiLink to="class/RequestQueueClient#batch_add_requests">`RequestQueueClient.batch_add_requests`</ApiLink> retries the skipped requests itself. Each retry sends only the requests the API hasn't processed yet.

You can customize this behavior using the following arguments of `batch_add_requests`:

- `max_unprocessed_requests_retries`: Defines the maximum number of retries, 3 by default. Set it to `0` to disable retries.
- `min_delay_between_unprocessed_requests_retries`: Sets the minimum delay before the first retry as a `timedelta`, 500 milliseconds by default. Each later retry waits about twice as long as the one before it.

Requests that are still unprocessed after the last retry are returned in `unprocessed_requests`. If a retry call fails, the client logs the error and returns the requests it didn't add as unprocessed.

## Request statistics

The client counts its calls, HTTP requests, and rate limit errors. To read the counts, use the <ApiLink to="class/ApifyClient#stats">`stats`</ApiLink> property. It returns a <ApiLink to="class/ClientStatistics">`ClientStatistics`</ApiLink> object with these fields:

- `calls` is the number of calls made through the client, including requests to Actor servers.
- `requests` is the number of HTTP requests sent, including retries and requests to Actor servers.
- `rate_limit_errors` maps each attempt to the number of rate limit errors it got. It counts 429 responses and the `batch_add_requests` rounds that return unprocessed requests. Key `0` is the first attempt, key `1` is the first retry, and so on. The field is a `defaultdict`, so reading a missing key adds it. To read a count without changing the dict, use `.get()`. Only API calls count here. A 429 from an Actor server called through <ApiLink to="class/ActorServerClient#request">`ActorServerClient.request`</ApiLink> is not counted.

With a custom HTTP client, `stats` returns the statistics of that client. For details, see [HTTP clients](/api/client/python/docs/concepts/custom-http-clients).

## Wait for resources to start a run

Starting a run fails with an HTTP 402 error when the account doesn't have enough free memory for the run, or when it already runs as many Actors as its plan allows. The error `type` is `actor-memory-limit-exceeded` or `concurrent-runs-limit-exceeded`. The client doesn't retry these errors on its own, since they clear only after other runs or builds of the account finish.

To keep retrying the start until the resources free up, set the `wait_for_resources` argument of <ApiLink to="class/ActorClient#start">`ActorClient.start`</ApiLink>, <ApiLink to="class/ActorClient#call">`ActorClient.call`</ApiLink>, or the same methods of <ApiLink to="class/TaskClient">`TaskClient`</ApiLink>. The client then retries the start every 10 seconds, and the argument value sets how long:

- `True` retries until the run starts.
- A `timedelta` stops retrying after that time and raises the last error.

Any other error raises right away. A run that asks for more memory than the account's whole memory limit gets the same `actor-memory-limit-exceeded` error and never starts, so with `True` the client retries it forever. In `call`, the time spent retrying doesn't count toward `wait_duration`.
